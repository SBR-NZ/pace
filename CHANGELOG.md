# Changelog

Versions use `MAJOR.MINOR.PATCH`. This file describes repository changes, not an installation receipt or an owner's approval.

## 3.16.0 - Numbered project folders

- **Each project folder is numbered**, so it keeps its place as more are added instead of moving with the alphabet. A folder starts with its number, a full stop and a space: at the top of `1 Projects/` from `01.`, and inside a project from `02.`, after the project's `01. Documents/`, as in `01. Kowhai Books/02. Budget 2027/01. Documents/`.
  - The full stop marks a number, so a name that starts with digits, such as `24 Hour Fitness` or `2026 Tax return`, is never read as one. A folder already named with two digits, a full stop and a space, such as `24. Dezember Feier`, counts as numbered.
  - A number is two digits, `01` to `99`, so folders list in order even where names are sorted as plain text, and it is not changed once given.
  - Only `Documents/` or `01. Documents/` is a project's Documents folder; any other number before Documents makes an ordinary folder.
- **New projects.** The record tool's `project-new` gives each new project one more than the highest number a project folder beside it has. It never takes a number a folder of the owner's own starts with, such as `99. Archive`, and takes a free one below when none is left above. Give it the name without a number: a name that starts with one is refused. Repeating the command still finds the same project, and a folder already there with that name, numbered or not and in any letter case, is used rather than a second one made.
- **Names stay plain.** Pages, chat and the tools' results show a project's name without its number, such as `Budget 2027`, and the record tool's `projects` gives each folder's `number`. `Repos/` mirrors projects by their names, with or without the numbers, so the references already there keep their places.
- **The folders tool**, `Product/Tools/pace_folders.py`, numbers the folders a Pace folder already has, on the owner's yes:
  - `preview` shows each new name and changes nothing. Each `Documents/` becomes `01. Documents/`. A folder that already starts with a number keeps it, and the other project folders take the lowest numbers free, in the order a file browser lists them now, as Windows File Explorer does near enough, so they keep their order among themselves; folders that are not projects keep their names, so those without a number come after the numbered ones. It warns that whatever finds a file by its path, such as a link between Excel workbooks or a Power Query or Power BI file source, stops finding it, and names any file whose path would then pass Excel's limit or reach Windows' usual 260 characters.
  - It leaves as they are, and says why: a folder reached through a link or junction; a project inside a folder that is not one, such as a repository checkout; a project that cannot be read, or whose name is not valid text or holds a line break, and everything in it; one that would have the same name as another beside it once numbered; and both Documents folders of a project that has two.
  - `apply` saves a record of the renames and reads it back before renaming anything. It renames each folder, the deepest first and whole folders at a time, never over a folder already there, and checks it. A folder that cannot be renamed keeps its name while the rest are renamed, a correction of the record says what happened to each, and a later run gives the folders still waiting the lowest numbers then free, in the same order, so each gets the number planned for it unless a folder beside it has been made, removed or renamed since.
- **Records keep working.** A record keeps the path it was saved with, and the tools find each file through folders that have since been numbered, as they already do for `Projects/` and the other folders renamed in 3.11.0. An update never renames a folder of yours, and once folders are numbered the updater will not install a release from before 3.16.0.
- The health check notes what the folders tool would still number, and what it cannot until the owner sorts it out, from the tool's own plan, and warns about a project with two Documents folders, saying to move each file into the one the tools use, never over a file of the same name.
- Help: projects (Numbered folders), records, confirmations, repositories, the health check and updates; `Pace.md` says where a project's files are, numbered or not. The example folder is numbered. Tests cover new projects, retries and existing folders, names that start with digits, Documents folders, plain names, older paths, the folders tool's preview, apply, refusals, links, checkouts, clashes, batches and failed renames, the health check, the updater and the help.

## 3.15.0 - Numbered items on the Project overview

- **Numbers on the overview pages**: each open item, and each item recorded two ways, has a number on the Project overview page, shown as "3.", so the owner can name it in chat, such as "3 is done" or "2 and 5 are due Friday". Numbers are given in the order the items first appear (recorded two ways, then Needs attention, then the rows from the top), and an item keeps its one number wherever else it appears on that page, the last 7 days included; done and cancelled items have none. The accounts of an item recorded two ways are lettered a, b and so on, so no number on the page means two things. Every view, every project, one project and by person, is numbered, and the chat summary gives the same numbers.
- **A number belongs to its overview.** Each numbered line keeps the request id of the item's current account in the page, never shown, and the overview tool's result lists every number with its request ids, subject and project, after everything else, so a later chat, a phone or Copilot included, finds the same item. The Project overview add-in has the steps:
  - use the overview made in that chat, otherwise the newest page in `2 Views/`, asking when that day has more than one or the chat also gave a weekly review list;
  - find each number there, never from memory or another list; where a host can read only the page's text, find the item by its subject and project, and ask if more than one matches;
  - show each item back with its subject and the change, and on the owner's yes save each change as a correction of its current account with `update-action`, read back; for an item recorded two ways, the owner first says which account stands.
- **A later chat finds the steps.** `Pace.md`'s add-in index now says that numbers belong to the list or page they came from, and the Project overview's purpose line and Claude launcher name numbers. An add-in index line already in your `Pace.md` stays as you wrote it; to use the new wording, copy the Project overview line from add-ins help. A Claude launcher you installed earlier keeps its old description until you install it again. The weekly review's list keeps its own numbers, and its add-in says so.
- **The page's text reads apart.** Each line's number, tag, subject and project, and each row's parts, have a space between them, which the page's layout ignores, so a host that reads only the text sees "3. 2 days late Board pack" rather than the parts run together.
- The page's lines have a narrow first column for the number. A customised template whose line grid has no column for it shows the number at the start of the subject instead, even when only its new styles were carried over. The template's note says how to number a page made by hand. When something could not be read, the result's message now says Partial.
- Tests cover the order of the numbers, an item keeping its number across the page, done and cancelled lines with none, each number's request id in the page and in the result, a corrected item, every view, an item with three current accounts, templates with and without the number column, the page's text, and the add-in's steps.

## 3.14.0 - Archiving finished work

- **Archiving** moves finished work out of `Record/` itself, so it stays quick to open on OneDrive's web pages and through a OneDrive connection, which slow down as a folder nears 5,000 items. An item's whole story, its first record and every correction, moves once its work is finished and every record in it is more than 3 months old: an action done or cancelled, a withdrawn item, a decision, a note, a result, a figure or a confirmation. Each record keeps its name and every byte, and goes into the folder inside `Record/` for the year and month in its request id, such as `Record/2026/07/`, so it can always be found from its id. Open work, work recorded two ways, project changes and everything from the last 3 months always stay directly in `Record/`, so open work and each project's owner, target and status can be read from it alone. A story with a missing record or corrections that loop stays, and so does every story in a project with a record that cannot be read or a second copy. New records are always saved directly in `Record/`, a correction of an archived record too, and nothing but archiving ever moves a record.
- A new tool, `Product/Tools/pace_archive.py`, does it on the owner's yes. `preview` changes nothing: it says how many records would move and where, how many items stay and why, and gives a plan. `apply` moves exactly that plan with the owner's go-ahead in their own words, and moves nothing if what would move has changed since the preview, or if asked to judge from a moment still to come. It moves the oldest first, as many as the record of the archive can list: up to 1,500 records, and down to about 850 when project ids are as long as they can be; a story too long for one archive's record stays in `Record/`. Before it moves anything it saves that record, a note from the owner with their words that lists every record it is moving under its month folder with a digest for each folder, and reads it back. Each record is then renamed into place, never copied or rewritten and never over a file already there, and checked to read back the same. If it stops part-way, for any reason, every record is still whole and in one place, and preview finds the rest.
- Every tool reads archived records where they are: the record tool's read, find, history, create, update-action, listing and confirmations; the overview tool's pages and review list; the health check; and the updater's check of a confirmation. A kept listing matches each file by its name, so a record archived since is still the same file. Which tools say what about the records is unchanged by archiving: tests compare every view, the review list, a search and a history before and after.
- The health check names anything inside `Record/` that archiving did not put there: a record outside the folder for its own year and month, a record in a month folder that no archive lists, a folder that is not a year or month folder, one record in two places, with the fix that keeps the copy its archive vouches for, and a month folder that cannot be read. It checks every record an archive lists against the record of that archive: in its month folder and, by the folder's digest, unchanged, or still directly in `Record/` when the archive stopped before moving it. Once `Record/` itself holds 2,000 records and at least 500 could move, it suggests archiving in a note, and the review list says so in one sentence; past 5,000 items with finished work to move, it is a warning with archiving as the fix. With nothing to move, it stays a note that nothing needs doing.
- The updater will not install a release whose tools cannot read archived records over a folder that has them, so going back to a release before 3.14.0 stops with nothing changed.
- `Pace.md`'s line for `Record/`, records help (a new part, Archiving finished work), the record format, the steps for working through a OneDrive connection, the health check help, the folder map and the Weekly review, Open work and Project overview add-ins say where archived records are and how to read them by hand. The example has a small archive from 2025, with the record of it.
- An independent review then tested the build, including 10,000 invented records, where the review list, the health check, preview and apply each take between one and two seconds, as before. Each of its findings has a test that fails on the reviewed commit. A full batch with long project ids would have been too long for the record of its archive; it is now kept to what one record can list, and the record is saved before anything moves. A hand-made record whose request id's time is not a real date and time stopped the health check, the review list and preview; it is now named and not read, and the record tool, like the others, always answers with one JSON object. Anything in `Record/` that was not read, such as a folder of the owner's own or a record out of its month folder, now makes searches and histories incomplete, stops `update-action` and confirmations, and stops archiving, as it already did the overview. A story moves only when every record in it can be relied on, whatever its project. A save's leftover copy of a record since archived stays housekeeping, the updater names an archived confirmation where it is, and on Linux the move asks the system itself never to replace a file.
- A second review then checked those fixes, and each of its findings has a test that fails on the commit it checked. A hand-made correction that names its earlier record by something other than a request id no longer stops the health check, the review list, preview or history. When the record of an archive cannot be read, the records it moved are no longer each called moved by hand; they are named once and judged when it can be read. A record an archive stopped before moving still counts towards its month's digest, since a rename keeps every byte. A retry after a stop that moved nothing goes ahead, a story too long for one archive's record stays without holding up the rest, an archived record that is there but cannot be opened is no longer called missing, a Python without ctypes still archives, and the health check reads each archived record once, as before. The overview tool, like the others, always answers with one JSON object.
- Tests cover which stories move and why the rest stays, the 3 months counted from each story's newest record, the batch, preview and apply, a failed move part-way, a file already in place, problems in the month folders, every tool reading archived records, a correction and a retry of an archived record, the health check's new findings, the updater's stop, the help and the example.

## 3.13.0 - Pace through a OneDrive connection, and Getting started

- **Through a OneDrive connection**: the hosts help has the steps for an assistant that reaches the Pace folder only through OneDrive or Microsoft 365, such as Claude on the web or phone, or Copilot. It opens `Pace.md` by its place rather than by search, which can find an older copy; lists `Record/` by reading the folder itself, every page, and calls a list made from search results, or from fewer than every page, partial; saves a record, and any other new file, with the setting that refuses a name already in use, or first checks the name where a host has no such setting, never replacing it or letting it take another name, and reads it back before calling it saved; never replaces, renames, moves or deletes a record or anything else Pace keeps as it is, such as `Pace project.md`, `Sources/`, `Archive/`, saved views, `Product/` and `Release record/`; changes `Pace.md` only on the owner's yes, reading it fresh straight before each change and checking the read-back shows that one change and nothing else; does by hand what Pace's tools would do where the help gives a way, saying that an update or a fingerprint needs a computer otherwise; and names the host in `by`. Claude on the web or phone has a line of its own among the hosts, Copilot's line points to the same steps as far as it can follow them, and the records, record format, add-ins and updates help point to them too.
- **Getting started** is a new shipped add-in, off until switched on, that sets up a new Pace folder with its owner, one question at a time: it checks what is already there with the health check, then the owner's name and time zone (asked, since a cloud assistant's clock is usually UTC), a short list of first projects, the add-ins to switch on (Weekly review and Project overview to start with), the assistants they use and the start of their assistant setup, a weekly review reminder where Weekly review is on and the host can set one that opens the Pace folder, and a plain word on backups. It changes nothing without the owner's yes, reads `Pace.md` fresh before each change and back after, sets up no account, connection or password, and ends with what was set up and anything left. It is offered, never started unasked: `Pace.md`'s add-in index says to offer it when the owner asks to set up Pace, and `get-pace.py` and the README suggest asking for it in the first chat. Add-ins help lists it first, and it has a Claude launcher.
- The health check points a folder to Getting started only when `Record/` and `1 Projects/` were both read in full and hold nothing, so a folder whose projects could not all be read is never called new; when Getting started is already on, it says to ask for it. From 4,000 items it notes how close `Record/` is to 5,000, counting every item in the folder as OneDrive does, past which OneDrive's web pages show a folder slowly or with errors. It is only a note, since syncing and Pace's tools are not affected and nothing needs doing, so a large `Record/` never stops a folder being healthy. On 10,000 invented records the review list takes about a second, so no other store of records is needed.
- An independent review then tested the build against invented folders and updates from 3.11.0 and 3.12.0. Each of its findings has a test that fails on the reviewed commit.
- Tests cover the connection steps and each host's pointer to them, the add-in's steps and limits, how a new owner is pointed to it, the health check's two new findings, and `get-pace.py`'s message.

## 3.12.0 - A weekly review, the owner's name, a health check and the owner's assistant setup

- **Weekly review** is a new shipped add-in, off until switched on, that goes through open work with the owner: anything recorded two ways first, then overdue work, work due today and in the next 7 days, work someone else owes with no due date, and the rest with no due date, oldest first. Items are numbered from 1 across the list and shown no more than 15 at a time. For each one the owner can say done, cancelled, a new due day, who owes it now or who it is for. Nothing they do not name changes, and nothing is saved until they confirm the list of changes in their own words; each change is then saved as its own correction and read back. With no one there to answer, such as on a schedule, it only makes the list. Add-ins help lists it with its line to switch it on, and it has a Claude launcher.
- The overview tool's `--review` gives that list for chat and saves nothing; with `--project`, for one project and the projects inside it. Each item carries a line ready for the chat, its current account's request id, its project, its due date or days open and who owes it. Work due later is counted, not listed.
- The record tool's new `update-action` saves a correction of an action's current account that changes its state, due day, who owes it or who it is for. It carries over the action's subjects, sources, every other header line and its text, and adds the change in plain words, so closing or moving work can never drop who owes it; who said it and when come from the update. It reads every record in the project, so it always finds the current account, and refuses any other account, an item whose corrections loop, an item with a second copy or an unreadable record that could be part of its story, a request id in another project and a change that changes nothing. For an item recorded two ways it says to withdraw the account that does not stand first. A project whose folder is missing here does not stop it, and a retry with the same request id is already saved. Records help describes it.
- `create --corrects` and `history` now follow corrections through every record in the project, so a correction whose request id is earlier than the record it corrects, as a computer with a wrong clock can make, still counts. Before, it was missed, and a second correction could be saved beside it.
- **The owner's name**: `Pace.md` has a new part, The owner's name, for `Owner:` lines that name the owner as records write them in `owed-by` and `for`, one line for each spelling. Only lines in that part are read, with or without a bullet, backticks, bold or quotes, so a standing instruction that starts "Owner:" is never taken for a name. The overview tool and the review list read them, so the owner's own work is no longer counted as someone else's when an assistant forgets `--owner`; `--owner` now adds a spelling for one run, and with neither the result says so. On the owner's records, without a name 45 items waiting on the owner showed as waiting on others. Like every Pace part, an update adds it to an owner's marked `Pace.md`, before Time zone, and never changes the owner's lines. The Project overview and Daily brief add-ins take the name from there, and the overview add-in no longer gives a real person's name as its example.
- **Health check**: a new tool, `Product/Tools/pace_check.py`, looks over the whole Pace folder and changes nothing. It lists, problems first and each with what to do, advice the tools can follow and that never replaces a saved record: missing folders, and folders still under their names from before 3.11.0, said once when projects cannot be read rather than once for every project; a `Pace.md` that updates cannot keep current, parts the owner changed, a missing `Owner:` line (with the names records most often give), a time zone that cannot be used, add-in index lines whose file is missing or that are not index lines, and lines naming old folders; files in `Record/` that are not records, second copies, records that cannot be read, corrections of missing records, corrections that loop, items recorded two ways, targets that are not dates and project ids that no project has, said once, and only as a warning when not every project folder could be read, so a project is never made twice; a `Pace project.md` that cannot be read, two folders with one id, projects in the wrong parent and folders with no id; repository references naming an unknown project or out of their project's place, reading each folder once however it is reached; an unreadable release note, an update left part-way and edited Product files; and the owner's assistant setup missing or not checked in 90 days. With `--latest` it also asks the release repository which release is newest, fetching nothing. It always prints one JSON object, even on an unexpected error or a file name that is not valid text, as the record and overview tools now do too. A new help page, Health check, describes it; `Pace.md` links to it, and updates help and the README suggest it after an install.
- **The owner's assistant setup**: `3 My add-ins/Assistant setup.md` lists the assistants the owner uses and what each can reach: where it runs, how it reaches the Pace folder, its skills, connections and scheduled tasks, and what it cannot do. `Pace.md` points to it from Where things belong, and the hosts help gives a template and says how it is kept: each assistant writes only what it can see of its own setup, on the owner's yes, and never a password, key or token. The updater no longer lists a file there as one of the owner's add-ins. The folder map names it and the health check.
- Files that Finder and Windows Explorer leave in folders, such as `.DS_Store` and `desktop.ini`, are no longer taken for edits to Product, so they no longer stop an update or make the health check ask for attention. A link kept under an old folder name that leads to its numbered folder, such as `Projects` to `1 Projects`, needs no renaming, so neither the updater nor the tools ask for one.
- The example's Product copy now matches the shipped Product exactly: it was missing the licence and parts of three help pages, two of them linked from its own `Pace.md`. The example has an Owner line, Weekly review switched on and an invented assistant setup.
- An independent review then tested the build against invented folders. Each of its findings has a test that fails on the reviewed commit. The create-only host tests now refuse deletes on Python 3.9 as well, so the whole suite passes there.
- Tests cover the review list's groups, order, numbering, lines, scope and refusals; `update-action`'s carried-over fields, plain-words changes, retries and refusals; Owner lines, how the overview and review use them, and an update adding the part; each kind of health check finding, that the check changes nothing, finds its own folder and asks the release repository only when told; the assistant setup help, template and example; and that the example carries the shipped Product.
